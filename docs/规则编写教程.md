# 规则编写教程

> 面向律师与二次开发者：如何让星星脱敏准确识别你所在团队的业务敏感信息。

规则决定「什么算敏感信息」以及「怎么脱敏」。内置规则覆盖身份证、手机号、住址、银行卡、
姓名、案号等常见类型；各律所、各业务线还会有自己的敏感词（项目代号、客户简称、
内部编号、特定格式的合同号），这部分用自定义规则解决。

---

## 1. 规则存放在哪里

首次启动时，内置规则写入本机应用配置目录：

| 系统 | 路径 |
| --- | --- |
| macOS | `~/Library/Application Support/cn.luminar.app/rules.json` |
| Windows | `%APPDATA%\cn.luminar.app\rules.json` |

界面「设置 → 打开规则文件」可直接编辑。程序在启动时读取；界面里保存规则会立即写回并生效
（点「重新识别」应用到已导入文档）。

文件结构：

```json
{
  "version": 1,
  "rules": [ { ...规则... } ]
}
```

`version` 预留给未来迁移，勿删。

> 手写 JSON 时可以只写 `name` / `kind` 与必要字段，`id`、`category`、`confidence`、
> `strategy` 等缺省时程序会自动补默认值（`id` 首次保存后固定下来）。

---

## 2. 在界面里新增一条规则

1. 顶栏「规则管理」→ 左下「新增规则」；
2. 填名称、选分类（自定义分类可选「自定义」，系统会沿用规则里的中文名）；
3. 选类型：正则表达式 / 关键词列表；
4. 填写表达式（或每行一个关键词）；
5. 设置基础置信度（0.3–1.0）与脱敏方式；
6. 在「规则测试」里粘贴一段真实（但已脱敏）的样例文字，点「测试匹配」；
7. 「保存规则」→ 关闭窗口 → 点右栏「重新识别」。

> 覆盖范围：保存后会对**当前已导入的所有文档**重新识别；识别结果中的自动标记会被替换，
> 你手工补的标记永远保留。

## 3. 字段详解

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | string | 唯一标识。内置规则以 `builtin_` 开头；自定义建议 `custom_` 开头 |
| `name` | string | 显示名称 |
| `category` | string | 分类 id（决定高亮颜色与统计口径） |
| `category_label` | string | 分类中文名（自定义分类时显示在清单里） |
| `kind` | `regex` / `keyword` / `ner` | 规则类型；`ner` 仅内置人名规则使用 |
| `pattern` | string | 正则表达式（`kind=regex`） |
| `keywords` | string[] | 关键词列表（`kind=keyword`） |
| `capture_group` | number | 取第几个捕获组，0 = 整段 |
| `confidence` | number | 基础置信度；低于界面阈值的自动结果不展示 |
| `strategy` | object | 脱敏方式，见下文 |
| `validator` | `none` / `id_card` / `luhn` / `uscc` | 二次校验，校验通过 +0.02，失败 ×0.85 |
| `priority` | number | 冲突时的优先级，越大越优先 |
| `enabled` | bool | 是否启用 |
| `require_boundary` | bool | 前后不能紧贴字母/数字（防止从长串中截取） |
| `case_insensitive` | bool | 正则/关键词忽略大小写 |
| `builtin` | bool | 是否内置（仅用于界面标记） |
| `description` | string | 规则说明，便于团队协作 |

### 脱敏方式 `strategy`

```json
{
  "kind": "mask",
  "mask_char": "*",
  "keep_prefix": 3,
  "keep_suffix": 4,
  "placeholder": "【{type}】"
}
```

- `kind = mask`：掩码遮蔽。`keep_prefix` / `keep_suffix` 保留前后若干位；
  手机号默认保留前 3 后 4，得到 `138****5678`。
- `kind = placeholder`：占位标签。`placeholder` 支持两个记号：
  - `{type}` → 分类中文名，如 `【身份证号】`
  - `{index}` → 同类序号，从 1 开始（模板里写了才会替换）
- `kind = delete`：直接删除，不保留任何字符。

## 5. 正则速查（法律文书常用）

Rust `regex` 语法与 PCRE 接近，但有两点必须注意：

1. **不支持后行断言** `(?<=…)`、`(?<!…)`；需要“前面不是数字”时，把前面的边界写进表达式
   并用捕获组，或勾选「边界校验」。
2. **默认不跨行**：`.` 不匹配换行；全文识别时 PDF 的折行已被去掉，Word/TXT 的段落边界保留。

| 需求 | 表达式 |
| --- | --- |
| 中文字符 | `[\u4e00-\u9fa5]` |
| 数字 | `\d` 或 `[0-9]` |
| 18 位身份证 | `\d{17}[0-9Xx]` |
| 手机号 | `1[3-9]\d{9}` |
| 银行卡 | `\d{13,19}` |
| 日期 | `\d{4}年\d{1,2}月\d{1,2}日` |
| 全角括号案号 | `[（(]\s?\d{4}\s?[）)]\s?[\u4e00-\u9fa5]{1,4}\d{0,4}[\u4e00-\u9fa5]{1,3}\d{1,6}\s?号` |
| 律师执业证号 | `1\d{16}` |
| 合同编号 | `[A-Z]{2,6}[-－]?\d{4,12}` |
| 车牌号 | `[京津沪渝冀豫云辽黑湘皖鲁新苏浙赣鄂桂甘晋蒙陕吉闽贵粤青藏川宁琼][A-HJ-NP-Z][A-HJ-NP-Z0-9]{4,5}[A-HJ-NP-Z0-9挂学警港澳]` |

> 正则里写 `\u4e00` 是四位十六进制写法，Rust `regex` 支持；也可以写 `\u{4e00}`。

## 6. 十个可直接抄的例子

### 6.1 仲裁案号

```json
{
  "name": "仲裁案号",
  "kind": "regex",
  "category": "case_number",
  "category_label": "案号",
  "pattern": "[（(]\\d{4}[）)]\\s?[\\u4e00-\\u9fa5]{1,6}仲字第?\\d{1,6}号",
  "confidence": 0.92,
  "strategy": { "kind": "placeholder" }
}
```

### 6.2 执行案号（含“执异”“执复”）

```json
{
  "name": "执行案号",
  "kind": "regex",
  "category": "case_number",
  "category_label": "案号",
  "pattern": "[（(]\\d{4}[）)]\\s?[\\u4e00-\\u9fa5]{1,4}\\d{0,4}执[\\u4e00-\\u9fa5]{0,3}\\d{1,6}号",
  "confidence": 0.92,
  "strategy": { "kind": "placeholder" }
}
```

### 6.3 律师执业证号（17 位，以 1 开头）

```json
{
  "name": "律师执业证号",
  "kind": "regex",
  "category": "custom",
  "category_label": "执业证号",
  "pattern": "1\\d{16}",
  "require_boundary": true,
  "confidence": 0.85,
  "strategy": { "kind": "mask", "keep_prefix": 4, "keep_suffix": 4 }
}
```

### 6.4 客户简称（关键词）

```json
{
  "name": "客户简称",
  "kind": "keyword",
  "category": "custom",
  "category_label": "客户名称",
  "keywords": ["江城置业", "江城置业的关联公司", "JCZY"],
  "case_insensitive": true,
  "confidence": 0.95,
  "strategy": { "kind": "placeholder", "placeholder": "【客户】" }
}
```

> 关键词按「包含」匹配，长词优先。上例中「江城置业的关联公司」会先于「江城置业」命中。

### 6.5 所内项目代号

```json
{
  "name": "项目代号",
  "kind": "regex",
  "category": "custom",
  "category_label": "项目代号",
  "pattern": "(?:星河|灯塔|青松)[-—－]?[A-Z]?\\d{2,6}",
  "confidence": 0.9,
  "strategy": { "kind": "delete" }
}
```

### 6.6 邮箱（只脱敏 @ 前的用户名）

```json
{
  "name": "邮箱用户名",
  "kind": "regex",
  "category": "email",
  "category_label": "电子邮箱",
  "pattern": "[A-Za-z0-9._%+-]+(?=@)",
  "confidence": 0.95,
  "strategy": { "kind": "mask" }
}
```

> 这个表达式用了先行断言 `(?=…)`，Rust `regex` **不支持**，仅作反例。正确写法：
> 命中整个邮箱，用掩码保留 `@` 之后的部分（内置规则已按此处理）。

### 6.7 护照号

```json
{
  "name": "护照号",
  "kind": "regex",
  "category": "custom",
  "category_label": "护照号",
  "pattern": "[EGDSPH]\\d{8}",
  "require_boundary": true,
  "confidence": 0.9,
  "strategy": { "kind": "mask", "keep_prefix": 1, "keep_suffix": 2 }
}
```

### 6.8 港澳台通行证

```json
{
  "name": "港澳通行证",
  "kind": "regex",
  "category": "custom",
  "category_label": "证件号码",
  "pattern": "[CWH]\\d{8,10}",
  "require_boundary": true,
  "confidence": 0.85,
  "strategy": { "kind": "mask" }
}
```

### 6.9 对公账户（只匹配“账号：”后面的数字）

```json
{
  "name": "对公账号",
  "kind": "regex",
  "category": "bank_card",
  "category_label": "银行账号",
  "pattern": "(?:账号|账户|卡号)[：:\\s]{0,2}(\\d{10,25})",
  "capture_group": 1,
  "confidence": 0.92,
  "strategy": { "kind": "mask", "keep_suffix": 4 }
}
```

> `capture_group: 1` 让命中范围只包含括号里的数字，不包含「账号：」三个字。

### 6.10 去掉“住址”前缀

内置住址规则已经会裁掉「住」「住址：」「地址：」等前缀。自定义时如需同样效果，
把前缀放进捕获组之外：

```json
{
  "pattern": "(?:住址|地址)[：:\\s]{0,2}([\\u4e00-\\u9fa5\\d]{6,60}(?:路|街|号|室))",
  "capture_group": 1
}
```

## 7. 置信度与阈值怎么配合

- 每条规则有基础置信度，命中后可能被校验器微调（身份证校验位、银行卡 Luhn、统一社会信用代码）。
- 界面顶部的阈值滑块是「展示门槛」：低于阈值的自动结果不会出现在清单里。
- 保守做法：阈值 0.8–0.9，宁可少标，靠人工补标；效率做法：0.65–0.75，多标再取消。
- 人工标记固定 100%，不受阈值影响。

---

## 8. 冲突与优先级

同一段文字可能被多条规则命中（如银行卡号也是 16 位数字）。消解规则：

1. 先按起点排序；
2. 起点相同取更长的；
3. 再比置信度、规则优先级；
4. 已接受区间与新区间重叠则丢弃后者。

因此：给范围更精确的规则更高的 `priority`（如「对公账号」> 「银行卡」）。

---

## 9. 调试技巧

- 规则面板的「测试匹配」只对当前输入样例生效，不会改动文档；
- 想看完整命中与坐标：用命令行工具
  `cargo run --example pipeline -- 你的文件.docx /tmp/out`，会打印每条命中的
  起止下标、分类、置信度与来源；
- 日志里 `source` 字段：`regex` / `keyword` / `ner` / `propagated` / `manual`，
  能快速判断是规则命中的还是人工补的；
- 修改 `rules.json` 后必须重启或点「重新识别」，程序不会自动监听文件变化。

---

## 10. 备份与迁移

- 整个 `rules.json` 可直接复制到另一台机器的同路径，实现团队统一规则；
- 升级程序不会覆盖已有 `rules.json`；只有点「恢复内置」才会重置；
- 建议把团队规则纳入 Git 管理（注意不要在规则里写真实客户名称）。
